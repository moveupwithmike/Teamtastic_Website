# 11 — Native Booking System

Fully native as of this snapshot — no Calendly in the primary path (Calendly survives only as a fallback link if `/api/bookings/config` fails to load). Covers new bookings, self-service manage (cancel/reschedule), Zoom/Google Calendar provisioning, and reminders.

## Components

**`BookingScheduler.js`** (new-booking flow, `/book`): fetches `GET /api/bookings/config` on mount; on failure renders a "warming up" panel with a Calendly fallback link rather than an error. State machine: type → date → live slots (`GET /api/bookings/availability?date&type&timezone`, refetched per date) → slot → contact form → Turnstile → `POST /api/bookings/confirm`. Client validation: trimmed non-empty name, email regex, non-empty Turnstile token (submit button also `disabled` without one). Errors map through a fixed `CONFIRM_ERROR_MESSAGES` table; unmapped reasons and network exceptions fall back to a generic message. Success screen shows local time + Zoom `joinUrl` if present — no manage/reschedule link shown here (only ever sent via email).

**`BookingManage.js`** (`/book/manage/[token]`): `idle → cancel|reschedule`. Cancel posts `{token, turnstileToken}` — note it **never sends `reason`** even though the API/DB support one end-to-end (a partially-built feature). Reschedule has its own duplicated copy of the date/slot-picking logic from `BookingScheduler` (not shared). Both paths reset the single-use Turnstile token on failure. The reschedule success screen shows the new time/Zoom link but does **not** surface the new `manageToken` the API returns — so a user who reschedules without checking email has no way back into "manage this booking" until they receive the confirmation email (which does carry the correct link).

**`/book/manage/[token]/page.js`**: hashes the raw token (SHA-256) and looks up `bookings.manage_token_hash` — the raw token is never stored. Branches on booking status: not found → generic invalid-link message; `cancelled` → cancellation message; `rescheduled` → message that does **not** link forward via `rescheduled_to_id` even though that column is populated (data exists, never rendered); anything not `confirmed` or in the past → "already happened"; otherwise renders details + `<BookingManage>`.

## API routes

All three (`confirm`, `cancel`, `reschedule`) run on Node runtime, hand-parse JSON with a shared `clean()` sanitizer and a `fail(status, reason)` helper, and use the service-role Supabase client (RLS revokes `anon`/`authenticated` on `bookings`/`booking_types`/`booking_settings` entirely).

**`confirm/route.js`**: rate-limited (`sha256(ip:email)`, 5/10min) and Turnstile-checked before any DB write. All business validation/atomicity is delegated to the RPC `hold_booking_slot` — kill-switches, email/name validity, booking-type existence, minimum notice, booking horizon, daily cap, and slot-exclusivity via a Postgres `EXCLUDE USING gist` constraint (caught as `exclusion_violation` → `slot_unavailable`). After a hold succeeds: Zoom meeting, then Google Calendar event, sequentially. On Zoom failure: `fail_booking_hold` frees the slot immediately and an urgent `tasks` row is filed for human follow-up. On Calendar failure: same, plus the just-created Zoom meeting is rolled back. Final `UPDATE ... WHERE status='held'` guards the confirm step against races; a 0-row result rolls back both external resources. Confirmation email is best-effort (awaited but `.catch(console.error)`'d) so email failure never fails the booking.

**`cancel/route.js`**: rate-limited on `sha256(cancel:ip:token)`. The entire cancel is **one atomic UPDATE** — `WHERE manage_token_hash=? AND status='confirmed' AND starts_at > now()` — which doubles as both the auth check and the write, with no separate SELECT-then-write race window. A 0-row result returns a single non-distinguishing `409` regardless of whether the token was invalid, already cancelled, already started, or never existed — deliberately avoids an oracle for guessing valid tokens. Zoom/Calendar cleanup is best-effort and **silently swallowed on failure** (`.catch(() => {})`) — no task/log fallback, unlike `confirm`'s equivalent failure path. Auth model is a bearer capability token (256-bit, SHA-256-hashed at rest) — possession of the emailed link is the only "auth," by design (same pattern as Calendly). Not a missing-auth bug given the token entropy; just worth stating explicitly as the trust model.

**`reschedule/route.js`**: same rate-limit/Turnstile pattern. Three explicit phases: (1) `hold_booking_slot` for the new slot under a fresh `manage_token`/hash (old booking untouched if this fails), (2) Zoom+Calendar for the new slot (rolls back the new hold on failure), (3) flip new booking to `confirmed`, then flip the old booking `confirmed → rescheduled` with `rescheduled_to_id` set. If the old booking is no longer `confirmed` by phase 3 (double-submit race), the new booking is **kept**, not discarded — the anomaly is only logged to `agent_log`, meaning a double-trigger race can leave two confirmed bookings for one customer. Old Zoom/Calendar resources are cleaned up only after the new booking is fully confirmed, same silent-swallow-on-failure gap as `cancel`.

## Supporting libs

- **`booking-time.js`**: pure timezone/date math (DST-aware wall-clock↔UTC conversion, interval overlap), no I/O.
- **`google-calendar.js`**: OAuth refresh-token flow; `getCalendarBusyRanges` (availability only), `createCalendarEvent`, `deleteCalendarEvent` (tolerates 404/410 as success). 8s timeout on every call.
- **`zoom.js`**: Server-to-Server OAuth; `createZoomMeeting` (waiting room on, `join_before_host: false`), `cancelZoomMeeting` (tolerates 404).
- **`rate-limit.js`** / **`turnstile.js`**: shared by all three booking routes (see [18](18-Security-Auth-and-Rate-Limiting.md) for the full cross-route usage picture, including the one gap below).

## Database

`bookings.status` enum: `held, confirmed, completed, cancelled, rescheduled, no_show, expired, failed` — every value is reachable from somewhere in the code (`held`/`expired`/`failed` via `hold_booking_slot`/`fail_booking_hold`; `confirmed` via both booking routes; `cancelled`/`rescheduled` via their respective routes; `completed`/`no_show` only via the office-only RPC `apply_post_call_outcome`, i.e. staff-entered, never customer-facing). No orphaned enum values found. Key invariants are CHECK-constraint-enforced (`ends_at > starts_at`, hold rows must have `hold_expires_at`, confirmed rows must have `confirmed_at`), and slot-exclusivity is a `gist` exclusion constraint over the blocked-time range — this is what makes `hold_booking_slot` race-safe without app-level locking.

`send-booking-reminders` (Edge Function): authenticated by a static webhook secret, not JWT. Sends 24h/1h reminder windows and a no-show follow-up, each idempotent via a `reminder_*_sent_at` stamp. **Scheduling is unusually indirect**: not registered in `supabase/config.toml` at all (unlike every sibling function); instead a `pg_cron` job calls a SQL trigger function that reads the function URL + webhook secret from Supabase **Vault** at runtime and does an outbound `net.http_post`. That cron job, and both of the `system_config` flags it depends on (`booking_reminders_enabled`, `booking_email_enabled`), are **off by default** — three independent switches must all be flipped before this feature does anything, confirmed as deliberate/documented (`LEAD_FUNNEL_OPERATIONS.md`), not dead code.

## Gaps (ranked)

1. **`GET /api/bookings/availability` has no rate limit and no Turnstile**, unlike its three siblings — it's the only booking route that calls out to Google's freeBusy API per request, with zero abuse protection. Given the other three routes are all guarded, this reads as an oversight rather than a deliberate choice, and a read-only endpoint with an invisible side effect (quota burn) is a plausible target for silent scraping.
2. **Cancel/reschedule cleanup failures for Zoom/Calendar are silently swallowed** with no task/log fallback, inconsistent with `confirm`'s pattern of filing an urgent task on the equivalent failure — a stale Zoom meeting or calendar event could persist with zero operator visibility.
3. **Reschedule's new `manageToken` is returned by the API but never used by the client**, and the manage page's "rescheduled" branch doesn't render `rescheduled_to_id` even though it's stored — both directions exist in the data model but only one is wired into the UI.
4. **Cancellation `reason` is accepted end-to-end by the API/DB schema but the UI never sends one** — a partially-built feature (the field exists, nothing populates it).
5. **`send-booking-reminders` requires three independent manual activations** (cron `active`, `booking_reminders_enabled`, `booking_email_enabled`) and isn't self-documenting in `config.toml` like its siblings — easy to mistake for dead code without the ops doc.
6. A double-submit race on reschedule (old booking no longer `confirmed` by the time phase 3 runs) is logged as an anomaly but not prevented — could leave two confirmed bookings for one customer in a narrow concurrent-request window.
