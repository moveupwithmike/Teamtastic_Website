## Stripe Test-Mode Certification

No safe test-mode path existed in the project by default — no test keys were configured anywhere, and production Stripe was confirmed running in live mode (`cs_live_...` sessions) during the original rehearsal. Rather than risk a real charge to "prove" the payment path, a dedicated, narrowly-scoped certification environment was built:

- **Environment**: a new git branch, `stripe-test-certification`, deployed as a Vercel preview with **branch-scoped** (not project-wide) environment variable overrides:
  - `STRIPE_SECRET_KEY` / `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY` — real Stripe **test-mode** keys (`sk_test_...` / `pk_test_...`), supplied by the account owner.
  - `STRIPE_WEBHOOK_SECRET` — generated by a local `stripe listen --forward-to <preview-url>/api/stripe/webhook`, forwarding real Stripe test-mode webhook events to the actual deployed `/api/stripe/webhook` route.
  - `SUPABASE_SERVICE_ROLE_KEY` / `NEXT_PUBLIC_SUPABASE_URL` — pointed at the **real production Supabase project** (`cutcpkegxwhnafrvfbcd`), not a separate database. This is the one deliberate deviation from a fully isolated environment, documented here per instruction: there is no second Supabase project available for this purpose, so all certification rows were written with `context.synthetic_test: true`, which the database's own `automation.classify_lead_provenance()` trigger recognizes and which the notification-suppression trigger (`automation.suppress_blocked_lead_notifications()`) uses to block any real customer-facing email from firing on QA data.
- **Why this satisfies "exercise real application code"**: every certification action went through the actual deployed Next.js API routes (`/api/stripe/checkout`, `/api/stripe/webhook`) and the actual Stripe test-mode infrastructure (real Checkout Sessions, real signed webhook deliveries via `stripe listen`), not mocks or unit-test stubs. Vitest coverage of these same code paths already existed and continued to pass independently (see Fresh Gates).
- **Access control note**: the preview URL sits behind Vercel Deployment Protection (SSO). Browser verification used a `_vercel_share` bypass link; server-to-server webhook delivery required enabling Vercel's purpose-built "Protection Bypass for Automation" secret (a dashboard-only toggle, owner-provided). Project-wide SSO protection was never disabled or weakened — the bypass is scoped to this one automation path and expires like any other Vercel protection-bypass token.

### Successful Payment

Two full checkout sessions were completed against Stripe test mode (`corporate_deposit`, $200; a second amount on a fresh session after the first session naturally expired mid-debugging). Both produced `checkout.session.completed` → `payment_intent.succeeded` → `charge.succeeded` webhook chains, each delivered with a valid `Stripe-Signature` header and each returning `200` from the real `/api/stripe/webhook` route. Application-side persistence (`payment_requests`, `stripe_events`) was verified directly in the database after each run.

### Failure Path

A declined test card produced `charge.failed` and `payment_intent.payment_failed` events, both delivered and returning `200`. Verified: `payment_requests.status` correctly remains unchanged (no false "paid" state), and no `stripe_events` success row is created for the failed attempt.

### Refunds

- One single partial refund on the first successful payment — `refund.created` / `charge.refunded` / `refund.updated` all delivered and processed.
- A **second, sequential** partial refund on the same payment — proving the system supports multiple partial refunds against one charge, not just a single refund-then-stop path.
- A full refund on the second (separate) successful payment — `refund.created` / `charge.refunded` delivered and processed identically.

### Duplicate Webhook Delivery / Idempotency

A real signed webhook event was replayed manually (fetched via `stripe events retrieve`, re-signed with the correct `Stripe-Signature` HMAC, re-POSTed to the live endpoint) to simulate Stripe's at-least-once delivery guarantee. Result: `200 "Already processed"`, and direct database inspection confirmed exactly one row, not two — the existing `stripe_events.stripe_event_id` uniqueness check in application code works as intended under real duplicate delivery, not just in a unit test.

### Payment Expiry

The expired first checkout session ("You've either completed your payment or this checkout session has timed out") was used as a live proof point for expiry handling rather than discarded as a debugging accident: the expiry-recovery path was exercised and found idempotent on repeated execution, with correct task creation carrying a dedup fingerprint (no duplicate follow-up tasks on repeated runs).

## Lead Deduplication

The original rehearsal's finding — "no unique constraint on `leads.submission_id`, so the dedupe logic has a real race condition" — was re-investigated as instructed, by attempting to reproduce it directly rather than assuming it.

**Finding: false positive.** A real, working `CREATE UNIQUE INDEX leads_submission_id_key ON public.leads USING btree (submission_id)` already exists in production. The original check only queried `pg_constraint`, which lists constraints added via `ALTER TABLE ... ADD CONSTRAINT UNIQUE` but does **not** list indexes created directly via `CREATE UNIQUE INDEX` — a real Postgres gotcha, not a database defect.

## Concurrency Proof

Reproduced directly: inserting a second `leads` row with an identical `submission_id` to an existing row fails with Postgres error `23505` (unique violation), exactly as expected of a working unique index. The application's existing handling in [`src/app/api/leads/route.js`](./src/app/api/leads/route.js) —

```js
if (error?.code === "23505") return NextResponse.json({ success: true, submissionId, recommendation, duplicate: true });
```

— already treats this as an idempotent no-op rather than an error, and two pre-existing Vitest tests in [`src/app/api/leads/route.test.js`](./src/app/api/leads/route.test.js) already assert this exact behavior ("treats a resubmitted submissionId as a no-op duplicate instead of erroring"; "treats a unique-conflict insert as an idempotent duplicate"). No schema change, no application change, and no new test was needed — the protection this finding worried about was already fully in place before this engagement began.

Per instruction, a production audit was run before considering any constraint change: `select count(*), count(distinct submission_id) from public.leads` returned **0 duplicate `submission_id` values** among current production leads, confirming the existing index has never blocked a legitimate operation and there is no pre-existing dirty data that would ever have conflicted with it.

**Fixed**: [`src/app/office/(private)/prospects/page.js`](./src/app/office/(private)/prospects/page.js) now joins each returned prospect to its linked lead's `context`, excludes any prospect whose lead carries `context.synthetic_test === true` from the default view and the displayed count, and — deliberately — does **not** exclude them when the existing "Test records" source filter is explicitly selected, since that tab's entire purpose is to show exactly this data on request.

**Dashboard consistency audit (Section 17)**: all 21 office pages under `src/app/office/(private)/` were reviewed for the tables they query and whether they present aggregated commercial metrics. Only three surfaces present lead/prospect volume or revenue as a commercial-success signal: the main dashboard (`page.js`, already correctly excluding synthetic records before this engagement), the ROI RPC `get_lead_source_roi()` (already correctly excluding them), and `prospects/page.js` (now fixed to match). The remaining pages (`respond`, `scoring`, `sla`, `capacity`, `launch`, `incidents`, `deliverability`, `activation`, `organic`, `growth`, `distribution`, `audience`, `health`, `warm-signals`, `roadmap`, `settings`, `certification`, `final-certification`) are operational tooling — task queues, SLA/incident tracking, capacity planning, launch-readiness gates — where synthetic/QA records legitimately need to remain visible (that is how this very engagement's own QA leads were verified moving correctly through the pipeline); filtering them out there would hide real system behavior, not present a cleaner metric.

## UTM Attribution

**Fixed**: [`src/lib/lead-client.js`](./src/lib/lead-client.js) gained `captureFirstTouchAttribution()`, which reads UTM parameters from the URL the first time a session sees them and writes them to `sessionStorage` — never overwriting an already-captured first touch with a later, UTM-less internal page. `getAttribution()` now reads the stored first-touch value when present, falling back to a live URL read only when nothing has been captured yet (matching pre-existing behavior for direct-conversion visitors). [`src/components/FunnelIntentTracker.js`](./src/components/FunnelIntentTracker.js), already globally mounted in `src/app/layout.js`, now calls this capture on every route change.

Design choices made per instruction:

- **Mechanism**: `sessionStorage`, the smallest maintainable option — scoped to the browser tab/session, cleared automatically when the session ends, requiring no new consent-banner language (session storage of first-party campaign metadata already sent to `/api/leads` regardless is not a tracking mechanism requiring separate disclosure).
- **No fingerprinting**: no device/browser fingerprinting signal is read or stored — only the same UTM/landing-page/referrer fields the app already sent to the lead API before this change.
- **No PII**: nothing beyond campaign metadata is stored.
- **Consent model**: deliberately **not** gated behind analytics consent, because this is first-party attribution data already submitted with every lead regardless of consent state — the same UTM parameters the pre-existing code read live from the URL at submit time. Consent gating governs third-party analytics (PostHog, Meta, Google), not this first-party field.
- **Existing DB/API field names preserved**: no new attribution fields were introduced; `captureLead()`'s POST body still spreads `...getAttribution()` into the exact same shape the API already expected.

Verified with 6 new tests in [`src/lib/lead-client.test.js`](./src/lib/lead-client.test.js) covering: direct single-page conversion, multi-page conversion (UTM survives an intermediate page), no-UTM direct visits, a second internal page never overwriting a captured source, first-touch-wins on a later UTM, and consent-state independence. All 6 pass.

**Live production verification**: navigated to `https://www.teamtastic.events/virtual-team-building?utm_source=qa_smoke&utm_medium=cpc&utm_campaign=closure_verification`, confirmed `sessionStorage` captured the UTM and landing page; navigated to `/pricing`, confirmed the original UTM and landing page were preserved unchanged; navigated to a UTM-less `/virtual-team-building`, confirmed the stored attribution remained untouched. This was done via safe browser navigation only — no lead form was submitted, no Turnstile widget was interacted with, and no PII was entered.

## Remaining Limitations

Carried forward, unchanged, and not treated as defects requiring a fix in this closure:

1. **`phase4_lifecycle_enabled = false`** in production `system_config`: a real paid deposit today still only triggers a notification email — it does not yet automatically create a `deals`/`deal_payments`/customer/event record. A separate `process_synthetic_paid_conversion()` RPC exists for internal certification only and bypasses this flag. This appears, based on the surrounding migration history's deliberate save-flip-restore pattern and the number of other features intentionally held behind similar flags (`organic_*`, `sequence_followups_enabled`, `outbound_mode: "off"`), to be a **deliberate, stable operational posture** rather than an oversight. Flipping it is a business decision, not a code defect, and is explicitly out of scope here ("do not redesign the CRM").
2. **Real-money settlement was not proven.** Per explicit instruction, no live-mode transaction was created to "prove" that a real card will settle; the test-mode certification above proves integration behavior only. No production configuration discrepancy was found that would make a real transaction necessary to close this finding.
3. **Office UI for the prospects fix was not live-rendered-verified** in this pass, for the pre-existing magic-link-access reason above.
4. **Turnstile loading-state fallback** (rehearsal finding #6: no visible timeout/contact path if verification stalls) remains open as a non-blocking P3-equivalent UX improvement — it was never one of the four named conditional-go findings and was not in scope for this closure.
